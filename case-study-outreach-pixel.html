#3 How It Works

How emails are generated & sent.

Every email is built at runtime HTML constructed, pixel injected, then sent via Gmail API.

📋 Step-by-Step Flow
🗄️
Postgres DB stores everything
Name, email, 5 messages, step number, thread ID, next send date
⏰
Schedule trigger every 30 min
Code node converts date → ISO string for exact SQL match
🔀
Switch node routes by step 1–5
Each step has its own code node reading the correct message field
{ }
Code node builds HTML email
Wraps text in <p> tags, appends invisible tracking pixel at bottom
📧
Gmail API sends or replies
Step 1 = new email. Steps 2–5 = reply using saved thread_id
✅
DB updated after every send
status → sent, step+1, next date = +3 days, thread_id stored
🔧 What the Code Node Does
📝
Parses raw text → clean HTML
Splits on newlines, wraps each block in <p> tags for Gmail rendering
🔗
Builds unique pixel URL
Encodes eid, to, c (campaign) into GET params per email
🕵️
Injects 1×1 invisible pixel
Hidden <img> at bottom loads silently when recipient opens
// Pixel injected at bottom of every email <img src="https://yoursite.com/track-open ?eid={{id}}&to={{email}}&c={{campaign}}" width="1" height="1" style="display:none;" />
💡 Why HTML not plain text?
Plain text emails can't embed an <img> tag so no pixel, no webhook, no tracking. HTML is the foundation.

📋 Raw Schema
CREATE TABLE public.out_duplicate (
  id         TEXT NOT NULL,
  name       TEXT,
  contact    TEXT NOT NULL,    -- primary key · unique per prospect
  threat_id  TEXT,             -- Gmail thread ID for reply chaining
  date       DATE,  time TEXT,
  message_1  TEXT,  message_2 TEXT,  message_3 TEXT,
  message_4  TEXT,  message_5 TEXT,  -- 5-step sequence
  step       INTEGER,          -- current step (1–5)
  subject    TEXT,
  status     public.status_type DEFAULT 'waiting', -- waiting|sent|open|stop
  created_at TIMESTAMPTZ DEFAULT now(),
  CONSTRAINT out_duplicate_pkey PRIMARY KEY (contact)
);
#4 The Algorithm

Filtering real opens from bots.

Email scanners load your pixel immediately after send. Without a filter, your metrics are junk.

⚠️ The Hidden Problem
Gmail and Apple Mail run security scanners that load the tracking pixel seconds after the email is delivered before any human opens it.
📧Email Sent
→
🤖Scanner
→
🪝Webhook
→
❌Fake Open
🚨 Impact without filtering
Broken follow-up sequences. Inflated open rates. Automation fires next email too early. Dirty analytics.
✅ My Solution
Ignore any open that fires in under 2 minutes. Compare the webhook timestamp against the sent_at value stored in Postgres.
📡Webhook
→
🧮Diff = open − sent
→
🛡️<2 min?
→
🚫Ignore
⏱️ Why 2 minutes?
Safe buffer above scanner speed (<30s) but below realistic human read-time. Keeps automation sequencing intact.
🛡️ Time Gap Guard Code Node Logic
const sentAt = parseInt(query.st || '0'); // stored in DB at send time const openedAt = $now.toMillis(); // webhook fires NOW const diffMins = (openedAt - sentAt) / 1000 / 60; if (sentAt > 0 && diffMins < 2) { return []; // 🤖 scanner fired too fast → discard } // ✅ real open extract eid, recipient, campaign, IP, user-agent // → update Postgres status to "open"
🎯
✓ Only real human opens are counted
✓ Automation sequences run without conflicts
✓ Clean data = better follow-up timing = more replies
★ Clean signals matter more than more signals.
